Spending Fewer Tokens

Every way to make Claude Code and Golden Thread use less of your allowance: what to turn on, how, what you will notice when it is on, and what you give up.

A Golden Thread guide, written against gt 0.22.1 (figures not re-measured for 0.22.0 are marked 0.21.4). Figures are labelled: measured (a run or a recorded event produced it, on the author's machine), estimated (worked out from a measurement), or not measured. None has been reproduced by anyone else yet.

One setting for all of it: usage_plan (new in 0.22.1)

Gt has a dozen settings that save tokens, and they work best when they agree with each other. usage_plan is one switch for the group, so you do not have to set them one by one:

usage_plan What it does
off No plan. Every setting is yours. Choosing off puts every setting back to what it was before the plan changed it (a setting you had never set is removed, so its default applies again).
min The safe few. Nothing is cut while you are working.
max min plus everything else in the table below. auto_clear is only ever set to shadow (it logs and never clears), because it has to prove itself first.
custom Your own mix. Shown automatically when you change a setting the plan set: custom (based on max). Change it back and it reads max again.

min and max save your current values the first time you leave off, then write the group. This is exactly what each one sets (generated from the same table the command uses, so it cannot drift):

Setting Default min max What it does
token_profile standard unchanged minimum Cheapest answers: terse replies, no skeptic pass, no vault hints, the average model profile.
farm_first suggest unchanged yes Hand routine work to your own local engines by itself (needs the farm module).
farm_ladder off unchanged on Route work through the engines you calibrated, cheapest first (needs the farm module).
farm_share off unchanged on Send a share of eligible tasks to hosted or local engines (needs the farm module).
cut_handoff facts facts facts What a cut carries into the fresh session: the findings and key facts.
cut_kind compact clear clear A cut is a clear with that handoff, not a /compact.
expiry_guard.handoff_pickup on unchanged on After a clear, load the saved handoff into the fresh session by itself (nothing to press).
auto_compact warn unchanged 250000 Cut the session by itself once its context reaches this many tokens.
auto_clear off unchanged shadow Score after each reply whether clearing would pay; only logs, never clears.
cut_advisor off suggest suggest Say once when a cut would pay back; never cuts.
expiry_guard warn-only auto auto Cut an idle session while its prompt cache is still warm.
context_nudge 40 30 30 Say once when the context passes this percent of the window.

A setting whose module is off (farm_ladder and farm_share need the farm module) is skipped and listed, never an error. Everything on the table has a default you can read with /gt:gt-settings <name>.

Turn it on and off: /gt-usage:usage-plan max (or min, off), or gt_settings.py set usage_plan max.

See exactly what it changed on this machine: /gt-usage:usage-plan changes (or gt_settings.py usage-plan changes) prints a table of setting, what it was, what it is now, its default, what it does, and the command that undoes it. It also marks any setting you have changed by hand since. /gt-usage:usage-plan show lists every member with its value now and its on and off commands. The same table is printed the moment you choose min or max.

Not the same as token_profile. token_profile trades answer quality against tokens, and its maximum spends more. usage_plan max is about saving, and it includes token_profile minimum. They share a word and nothing else.

Hold: no automatic cut in this session

Automatic cuts are the right default for a long day and the wrong one when you are mid-debug with exact values in the context. Hold stops all four automatic cuts for one session: auto_clear, auto_compact, the idle-session guard (expiry_guard) and the open-session path.

  • During a session: /gt-usage:usage-plan hold (and hold off to end it; hold status says whether it is on).
  • At the start of a session: launch with GT_HOLD_CUTS=1 claude. The session is held from its first prompt (the first hook that runs records it). Only one session can be held at a time, and a launch-time hold holds nothing while another live session's hold exists. The cut advisor still speaks in a held session, because nothing will cut it.
  • It ends with hold off, /clear or a new session. Resuming the same session keeps it. A held session that sits idle loses the cache-expiry protection, so coming back to it later can cost a full rebuild of its context.

Your sessions burn allowance fast? Do these, in this order

  1. Close or compact long sessions early. This is the biggest lever by far. Leave context_nudge at 40 so gt tells you when a session has grown, and leave auto_compact on its default (warn: gt says once when a session passes 150,000 tokens and never compacts by itself), or opt in with auto_compact auto (gt saves your work and compacts by itself at 150,000 tokens; auto_compact 50 cuts earlier). Two more settings shape each cut: cut_handoff (facts, the default, saves findings and a handoff with its key facts; handoff a handoff only; none a plain cut) and cut_kind (compact, the default, or clear: a fresh session that starts from the handoff). When you finish a piece of work, say "I'm done for now" (/gt:gt-close) and start a fresh session.
  2. Let gt trim sessions you walk away from. Set expiry_guard auto (the standard and minimum token profiles do this for you).
  3. Shrink what every session starts with. Keep startup_output compact (the 0.21.4 default), disable the gt plugins you do not use, and keep your CLAUDE.md files and memory index short.
  4. Keep big text out of the conversation. Turn on spill_threshold_lines 200 and paste_intake ask, and use /gt:gt-digest for a big file or log.
  5. Pick a token profile. standard is the default set; minimum spends least.
  6. If you run a model on your own computer, let it answer questions about your notes (vault_answers local-first) and take routine work (farm_first).
  7. For long working sessions, consider rules_injection compact.
  8. After a week, check what each mechanism actually saved with /gt-usage:gt-usage-savings. Keep what pays, turn off what does not.

To change any setting, type /gt:gt-settings <name> <value> in Claude, or just say it ("set auto_compact to 50"). /gt:gt-settings on its own shows them all with their current values.

Where your tokens actually go

Every time Claude replies, Claude Code sends it the whole conversation again: every message, every file Claude read, every command output. A prompt cache makes the repeats cheaper, but they are still paid for, on every turn, until the conversation is cut.

On a real multi-agent build, gt measured where the cost went (measured, 2026-10-15):

Part Share of the cost
Re-reading the conversation from the cache 73–74%
Writing new text into the cache 24–26%
Claude's written output 0.3–1.5%
Claude's thinking (part of the output) 0.1–0.9%

So cost is roughly the number of turns times the size of the conversation. A long session costs more per message the longer it runs. Everything in this guide does one of four things: fewer turns per session, a smaller conversation on each turn, less big text pasted or printed into it, or handing the work to something cheaper.

What barely matters: how long Claude's replies are, and its effort level. Cutting out all of Claude's thinking would save about 1% (estimated). Those settings change speed and how much you read, not your allowance.

What you give up. A compacted session is a summary of the old one, not every word. gt saves findings and a handoff first so nothing you would want is lost, but the exact wording of an early message is gone from the conversation.

The context nudge reads the session size from gt's status line (the gt-usage module); a default install sets no status line, so without it the nudge never speaks (add it with python3 ~/.claude/golden-thread/hooks/gt_usage.py --setup-statusline, or re-run the installer with --statusline yes). Auto-compact does not need the status line: it reads the session size from Claude Code itself, and runs only in terminal Claude Code.

2. Shrink what every turn carries

Some text rides along on every single turn: gt's start-up report, its rules, your CLAUDE.md files, the memory index, and the list of every installed skill and agent. Each token of it is re-read on every turn.

The author's own trim (measured, single runs, 2026-10-15): turning on the token-diet settings below and shortening the memory index and the vault's CLAUDE.md took the first turn of a session from 41,756 to 39,031 tokens, and cut what each later turn adds from about 1,351 to about 813 tokens.

Why the timestamp line matters. In the 90-run test of rules sent once (2026-10-15), Claude started its replies with a timestamp 84% of the time against 93% with the rules sent in full (measured). The rest held: tests before commits, no leaked keys. That is why 0.21.4 repeats the timestamp rule in the one-liner. Whether that closes the gap is not measured yet.

Keep the rules on. A separate 90-run test (2026-10-11) compared rules on with rules off: with them off, a correct result cost 1.26× as much, because Claude committed with failing tests and had to redo work; and a live key was pasted into the reply in 7 of 15 runs, against 0 of 15 with the rules on (measured). In one sentence: a correct result cost 1.26× as much with the rules off (90-run A/B benchmark on Opus, Sonnet and Haiku, 2026-10-11; every failed run re-prompted until correct; weighted by a real model mix). The rules pay for themselves; sending them once is the cheaper way to keep them.

Settings that add a line to every turn

Some settings are free. Others add one line of text to every turn, and some spend whole agents.

Costs nothing (shown only to you) Adds a line per turn Spends agents
prompt_hints: a "Tip:" line naming the command for what you typed vault_hints: up to three matching note titles skeptic_pass: an agent checks findings at each write-back

3. Keep big text out of the conversation

A 12,000-token paste costs about 15,000 token-equivalents when it arrives and about 1,200 more on every turn after it (estimated, from the cache prices). Big text is cheapest when it never enters.

Local engines are a modest lever today: most of the cost is long interactive turns that do not move. The guide Farming to Your Own Hardware covers setting one up.

A send must earn its keep (gt-farm, 0.21.4). Sending work to an engine also costs Claude tokens: the call, the packet when Claude wrote it, and reading the result. Each ledger line now records that as claude_overhead, and gt_farm_send.py ledger shows the net after it. From gt 0.22.0 the savings report's "Farmed packets" row is net the same way: it also takes off the output of a local review that reached your session and what a calibration's reference answers cost Claude, and a "Farmed savings by purpose" table under the main one shows what the net is made of. The overhead is an estimate (characters / 4, plus a fixed 220 tokens per send). Because of that, an automatic send of a packet under farm_min_chars (default 2000 characters) is skipped as "not worth sending" and stays in Claude; 0 turns the rule off, and a send you type is never skipped. The default is a first baseline from 88 sends on one machine (break-even near 1,360 characters), mostly probe traffic, so it is an estimate. An identical packet to the same engine and model is not sent twice inside farm_reuse_days (default 7; --fresh forces a send). Every packet is scanned for credentials before it leaves. A long send prints a "waiting" line every farm_heartbeat_s seconds (default 30; 0 is off).

Hosted spend: sample and how to set up your own

gt 0.22.0 ships a sample, not your setup: templates/hosted-spend.sample.md in the gt-farm module shows the two settings (usage_external, farm_budgets) and one service-table row for a made-up engine on a made-up host (example-provider, address ending .invalid). It holds no key, no account id and no real address, and gt does not read it.

What you get without doing anything else is an estimate: the tokens sent and received, at the rate in the engine's row. The status line says (estimated) and stays quiet until an engine is at 80% of its budget or was answered with a 429. gt 0.22.0 does not read a provider's balance or billing API; the balance_source column in the sample is reserved and ignored.

To set up your own: copy the row into your service table and change every value (name, address, model, rate from the provider's pricing page); put the engine's API key in a mode-600 file by a script you run (never in a session), named in key_file; then gt_settings.py set farm_budgets "yourname=10". For a measured balance you would also need a read-only billing key from the provider, kept in the secrets store and never entering the session or the repository. gt does not use one yet.

5. Use helper agents well

A helper agent (a subagent) does its reading in its own conversation and hands back a short answer. That keeps your main conversation small, but the helper itself is not free.

  • Give a narrow brief and ask for a short return. A helper that explores everything, or returns everything it read, moves the cost instead of saving it.
  • Parallel helpers cost the same as one after another (measured, 2026-10-15), and finish 3–4 times sooner (estimated). Run independent work in parallel.
  • Never fold many jobs into one long conversation. Doing all of a multi-agent build in one growing context was worked out at 2.35–5.4× the cost (estimated).
  • Do not hand a small read to a helper. Below about 18,000 tokens, reading it yourself is cheaper (see the size rule above).

Measure your own

Your numbers will differ from the author's. To see them:

  • /context inside a session lists what the conversation holds: system prompt, skills, agents, memory files, MCP tools and messages. claude -p "/context" prints the same for a new session without opening one.
  • claude plugin details <name>@golden-thread-plugin shows one plugin's always-on cost.
  • /gt-usage:gt-usage shows where you stand against the 5-hour and weekly allowance.
  • /gt-usage:gt-usage-savings shows what each gt mechanism saved and cost, with a net figure; a mechanism losing tokens over 7 days is flagged.

The three-turn check (before and after a change). Run three short turns in one headless session and read each turn's size. Turn 1 is what a session starts with; the difference between turns 2 and 3 is what each turn adds.

SID=$(python3 -c 'import json; print(json.load(open("t1.json"))["session_id"])')
claude -p "Say OK." --resume "$SID" --output-format json > t2.json
claude -p "Say OK." --resume "$SID" --output-format json > t3.json

What we do not claim

  • Every figure here comes from one person's machine and a handful of author-run tests. No other user has been measured.
  • Several levers have no number yet: auto-compact on a live session, long output kept out, big pastes held back, and rules sent once over a long session.
  • Local engines save little so far, and their answers were below Claude's quality in blind checks; gt audits them for that reason.

Appendix: how it works underneath

For readers who want the mechanics; nothing here is needed to use the settings.

  • The rules, hints, allowance and reply-length lines are added by gt's per-message hook. With rules_injection compact it checks that the full text is really in the conversation before it sends the one-line version, and sends the full text again when a rule changes.
  • The context nudge reads the session's size from the gt-usage status line (none is set on a default install). Auto-compact reads it from Claude Code itself; it runs only in terminal Claude Code, does nothing while a background task runs or within 6 turns of the last cut, and its busy check needs the background_tasks list in Claude Code's Stop payload (confirmed in 2.1.300): without it nothing is cut, and gt says so. /gt:gt-minimize compact needs Claude Code 2.1.296 or newer; below that nothing cuts and Claude tells you to type /compact. With cut_kind clear the in-session mod runs /clear through Claude Code's command API, at the same size auto_compact cuts at (the auto_clear policy keeps a shadow record, and clears only once on is allowed and was confirmed with the typed word; never while a background task runs or once your next turn has started); that has not yet been seen in a live Claude Code window.
  • Long output is kept out by a hook that runs after a successful shell command; the files are private to you and pruned after 7 days. gt_spill.py run -- <command> does the same for a command that fails.
  • Held-back pastes are scanned first, then saved to private files under ~/.claude/golden-thread/intake/ with any line that looks like a credential replaced by a [gt: line N withheld ...] marker (the block message says how many; sending the message again sends them too). Long command outputs are masked the same way. If the scan cannot run, nothing is saved and your message or output goes through as it is. Claude Code still keeps the prompt in your own prompt history.
  • /gt:gt-settings explain <name> prints the full technical description of any setting.
