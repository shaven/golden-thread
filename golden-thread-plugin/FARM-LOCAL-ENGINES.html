Farming to Your Own Hardware

Running open-weights models on machines you already own as gt-farm engines — what to measure, how to size a node, and how gt routes to it and counts the saving.

A Golden Thread paper, written against gt 0.22.0 and gt-farm 0.21.3. The figures are one owner's measurements on 2026-10-14, labelled self-verified (one run each, not independently reproduced). Your hardware will differ; the method is the point, and the first section tells you how to get your own numbers in an afternoon.

1. The claim, and what it rests on

A hosted coding model costs money per token. A machine you already own costs nothing per token. gt-farm already moves bulk, mechanical and second-opinion work out of the Claude session as a work packet with a strict return contract; since gt-farm 0.21.1 the packet can go to an engine on your own network, and gt records what it cost and what it would have cost elsewhere.

The claim is narrow. It is not that a local model replaces the interactive session. It is that the share of your spend that is mechanical — extraction, classification, freshness sweeps, test generation for a named function, a second opinion on a draft — can run on hardware that is idle most of the day, in parallel, at no marginal cost, and that gt can route it there and prove the saving.

Three measurements make the claim concrete, and section 3 shows how to repeat them:

What Where Result
A 30B-parameter mixture-of-experts coding model, 4-bit an ordinary mini-PC (8-core laptop-class CPU, no GPU) 15–22 tokens/s generating, 70–110 tokens/s reading the prompt
The same model, 4 requests at once the same mini-PC 40–52 tokens/s aggregate
A 120B mixture-of-experts model a laptop with 128 GB unified memory 89 tokens/s generating, ~940 tokens/s reading; 132 tokens/s aggregate over 4 requests

All self-verified. The surprise in the first row is that it works at all: for years the rule was "no large-model generation on a CPU". That rule was true of dense models and is false for mixture-of-experts models, and section 2 says why.

2. Why a CPU can generate now: bandwidth, not compute

Generating one token means reading every weight the token touches. A CPU is not short of arithmetic for that; it is short of memory bandwidth, and the time per token is, to a first approximation:

seconds per token  ≈  bytes read per token  ÷  memory bandwidth

A dense 30B model at 4 bits reads about 17 GB per token. At the 50–100 GB/s a desktop memory bus delivers that is 3–6 tokens/s on a good day: unusable. A mixture-of-experts (MoE) model of the same total size activates only a few of its expert blocks per token — a "30B-A3B" model has 30 billion parameters and about 3 billion active — so it reads about 2 GB per token instead. The same bus now gives 25–50 tokens/s as a ceiling, and in practice you see 40–50 % of the ceiling, because the arithmetic and the memory system do not overlap perfectly.

Three consequences follow, and every rule in this paper is one of them:

  1. Memory bandwidth decides the node, not core count. A laptop-class part with LPDDR5-6400 outran a desktop-class part with DDR4-3200 by only 15 %, and a six-year-old DDR4-2666 part was still usable. Core count and vector extensions mattered less than expected (unverified as a general rule: one run per host, variables not isolated).
  2. The weights must fit in RAM with room to spare. When the model file was larger than the free memory, the operating system paged weights in and out on every token and throughput collapsed to a third. Nothing warned; the numbers were simply bad.
  3. Several requests at once are nearly free. The server batches them, so one weight read serves several streams. On the mini-PC, 1 → 4 → 8 → 16 concurrent requests gave 22 → 40 → 52 → 64 tokens/s aggregate while each stream slowed. There is no sharp knee, only diminishing returns, so the default of four slots per node is a latency choice, not a limit.

The same arithmetic says what a GPU or a unified-memory laptop buys you: an Apple laptop with 546 GB/s of memory bandwidth ran the 30B-A3B model at 133 tokens/s, six times the mini-PC, and reads a 2,000-token prompt in 1.4 s where the mini-PC takes 20 s. That is the division of labour: the laptop is the interactive host and the fastest batch engine; the fleet of small machines is extra width for packets that have short prompts and long outputs.

3. Measure before you believe anything here

Every number above came from the same four commands, run in a throwaway virtual machine. Repeat them on your own hardware before planning around it; it takes an afternoon, most of it the model download.

The node. A Linux VM (Ubuntu 24.04 cloud image is convenient) with as many vCPUs as the host has physical cores, the CPU model passed through (cpu: host on Proxmox, or the equivalent), memory ballooning off, and RAM at least 6 GB above the model file you intend to run. 80 GB of disk is plenty. A bare-metal install works the same way; a VM is simply easier to delete.

The engine. llama.cpp's server, built on the node so the build uses that CPU's instructions:

sudo apt-get install -y build-essential cmake git curl libcurl4-openssl-dev
git clone https://github.com/ggml-org/llama.cpp ~/src/llama.cpp
cmake -S ~/src/llama.cpp -B ~/src/llama.cpp/build -DGGML_NATIVE=ON -DLLAMA_CURL=OFF
cmake --build ~/src/llama.cpp/build --config Release -j

The model. A GGUF file of a mixture-of-experts coding model. The measurements used Qwen3-Coder-30B-A3B-Instruct in two quantisations: Q4_K_M (17 GB) for a node that is dedicated to it, and UD-Q3_K_XL (13 GB) for a node that shares its RAM with other virtual machines. Download from the model's page on the model hub (curl -L -o ~/models/<file>.gguf <url>); the file is the only artefact, there is no installer.

The two measurements. First the engine's own benchmark, which reports prompt processing (pp) and generation (tg) in tokens per second:

~/src/llama.cpp/build/bin/llama-bench -m ~/models/<file>.gguf -t $(( $(nproc) - 1 )) -p 512,2048 -n 128 -r 3

Then the server, the way gt will use it, with four slots and a real request:

~/src/llama.cpp/build/bin/llama-server -m ~/models/<file>.gguf -t $(( $(nproc) - 1 )) \
    -c 16384 -np 4 --host 127.0.0.1 --port 8080 &
curl -s localhost:8080/v1/chat/completions -H 'Content-Type: application/json' -d '{
  "messages":[{"role":"user","content":"Write a Python function that parses an nginx access log line into a dict, with three pytest tests."}],
  "max_tokens":400,"temperature":0}' | python3 -c 'import sys,json; t=json.load(sys.stdin)["timings"]; print(t["predicted_per_second"], "tok/s")'

Run the request four times concurrently (for i in 1 2 3 4; do curl ... & done; wait) and read free -m before and after: if available memory went near zero, the node is paging and the numbers are not the node's, they are the disk's.

What to write down. For each node: CPU, memory type, RAM, the quantisation, pp512, tg128, the single-request server rate, the four-way aggregate, and whether memory stayed free. Label every figure with its verification state. One run is self-verified; it becomes independently verified when someone else reproduces it.

4. Sizing rules

From the measurements, in the order they bite:

Rule Why
Weights ≤ free RAM minus 6 GB. On a shared 28–32 GB node that means the 13 GB quant, not the 17 GB one. gt_farm_engine.py enforces this and refuses to install a model that does not fit. Paging collapsed throughput to a third and gave no warning.
Four slots per node by default (-np 4, context -c 16384); eight for pure bulk; sixteen only on a dedicated node where latency is irrelevant. 1.8× throughput at four slots for a 10 tokens/s packet; each further doubling adds only ~12 tokens/s while halving per-packet speed.
One model per node. Swap models by restarting the service, not by loading two. Two models double the paging risk and halve the slots.
Short prompts to the fleet, long prompts to the laptop (or a GPU). Prompt processing on a CPU is 70–110 tokens/s: a 2,000-token prompt is 20 s before the first output token.
Threads = physical cores minus one. Leaves the server and the OS a core; hyper-threads add nothing to a bandwidth-bound loop.
Bind the server to loopback, or to the LAN address only and behind the network's own boundary — never 0.0.0.0. There is no authentication in the engine. gt_farm_engine.py (section 5) binds loopback and refuses anything else. A chat endpoint is a free compute service for anyone who can reach it.

The projection those rules give for a fleet of eight mini-PCs at four slots each is about 32 packets in flight at ~10 tokens/s each (unverified: measured on one node of each class, extrapolated). A 1,000-token answer takes about 100 s. That is fine for a packet and wrong for a person waiting at a prompt, which is the whole division of labour.

5. Run the engine as a service, not from a Claude session

Once the numbers are in, the node stops being a benchmark and becomes something other things depend on: your sessions, and gt-farm. So the engine is a service of its own. A session talks to it over 127.0.0.1:<port>; it never owns the process.

Why not from the session. An engine started from inside a Claude session as a background task belongs to that session, and that costs you three ways:

  • It stops with the session. /exit, a compaction or a crash takes it down, and the 13–17 GB model has to be loaded again by hand. Observed on 2026-10-14: a llama-server launched as a session background task exited with code 144 (SIGTERM) the instant the session reaped it.
  • gt-farm needs a stable, always-on chat-completions endpoint (section 6). One that comes and goes with whoever happens to have a session open is not one.
  • It holds its memory for that session's lifetime, so closing a session to free context also tears down the engine you meant to keep.

A service decouples all three: it starts at login (or at boot), restarts if it crashes, and is the same process whichever sessions come and go.

The command

gt-farm ships gt_farm_engine.py (in the module's scripts/, beside gt_farm_send.py). It turns the recipe below into one validated command rather than a list of steps to follow by hand:

# 1. look first: prints the files and commands, changes nothing
python3 .../gt_farm_engine.py install engine-1 \
    --model ~/models/current.gguf --port 8080 --alias current --dry-run

# 2. install it: writes the service, loads it, waits for /health
python3 .../gt_farm_engine.py install engine-1 \
    --model ~/models/current.gguf --port 8080 --alias current

# 3. later
python3 .../gt_farm_engine.py check engine-1    # unedited, loaded, healthy
python3 .../gt_farm_engine.py status            # every engine it installed
python3 .../gt_farm_engine.py remove engine-1   # unload, delete what it wrote
Option Default What it does
NAME required Lower-case letters, digits and dashes. Part of the service's label and file names.
--model FILE required the first time The GGUF file; refused when it does not start with the GGUF header (a failed download leaves an error page). A split model (name-00001-of-00003.gguf) counts all its parts.
--port N required the first time The port on 127.0.0.1, 1024–65535. Refused when something already listens there.
--alias A NAME The model name the engine reports; the model column of the service table.
--context N 16384 Context size (-c), shared by the slots.
--slots N 4 Parallel requests (-np).
--threads N physical cores − 1 Threads (-t). Hyper-threads are not counted (section 4).
--llama-server FILE PATH, then the usual build locations The engine binary.
--host H 127.0.0.1 Accepts nothing else. See Loopback only below.
--system off A boot-time service; prints the sudo commands, never runs them.
--allow-low-ram off Install although the RAM rule refuses; prints a warning.
--wait S 180 How long to wait for /health before giving up and rolling back.
--check Change nothing. Exit 0 when nothing would change, 3 when something would.
--dry-run Print the files and commands. Change nothing.

Run it again with the same options and it changes nothing. Run it with different options and it replaces only what differs, backing the old file up first, and restarts the service. Run install NAME with no options and it reuses the ones it recorded.

Loopback only. The engine has no authentication, so it is bound to 127.0.0.1 and nothing else: --host 0.0.0.0, a LAN address or :: is refused, and no generated file names one. To reach an engine from another machine, keep it on loopback and put a boundary you own in front of it: an SSH forward (ssh -N -L 8081:127.0.0.1:8080 node, whose base_url is then http://127.0.0.1:8081/v1 on the machine that forwards), or a reverse proxy that authenticates.

On macOS

install writes two files and loads the service into your login session:

File What it is
~/Library/LaunchAgents/io.goldenthread.farm-engine.NAME.plist The service. RunAtLoad (starts now and at every login), KeepAlive (restarts on a crash), ThrottleInterval 10 (a crash loop cannot hammer the machine), output to the log. It runs /bin/bash …/llama-ctl.sh run.
~/.claude/golden-thread/farm/engines/NAME/llama-ctl.sh The control script holding the configuration. run execs the engine in the foreground, so launchd tracks the real process; start, stop, restart and status manage a detached copy by hand and must not be mixed with the service.

Beside the script are engine.log (the engine's output) and record.json, which lists every file the install wrote and a checksum of each: it is how check finds a hand edit and how remove knows what is safe to delete. The label is io.goldenthread.farm-engine.NAME, so an agent you made by hand earlier (for example com.local.llama-server) is never touched; stop that one first if it holds the port: launchctl bootout gui/$(id -u)/com.local.llama-server.

A LaunchAgent needs a logged-in graphical session. For a Mac that must serve with nobody logged in, use --system (below). Keep the model in a plain folder such as ~/models: a background service is usually refused access to ~/Documents, ~/Desktop, ~/Downloads, iCloud and the synced ~/Library/CloudStorage folders, and the install warns when the model is in one of them.

On Linux

The same install writes a systemd user unit, ~/.config/systemd/user/gt-farm-engine-NAME.service (Restart=always, RestartSec=10, WantedBy=default.target, output appended to the log; the log line needs systemd 240 or newer), and the same control script and record. A user unit stops when you log out unless lingering is on, so for a node that nobody logs in to run loginctl enable-linger $USER once; install prints that reminder. --system stages a system unit instead (below).

The RAM rule

The model file plus 6 GiB must fit in the memory the engine can use, or install refuses:

Machine Memory counted
Apple silicon 75% of the unified memory (the share the GPU may use)
Intel Mac free, inactive and speculative memory
Linux MemAvailable

An engine that does not fit pages its weights in and out on every token and throughput falls to about a third, with nothing to say why (section 4). So the command says it instead, with the numbers, and suggests a smaller quantisation. --allow-low-ram installs anyway and prints the warning; use it when you know something the command cannot, such as memory you are about to free. The rule is not applied to a re-run that changes nothing, and an engine of the same name that is already running does not count against itself when you change its model.

Proving it, and undoing it

install does not stop at writing files. It loads the service, then polls http://127.0.0.1:<port>/health for at most --wait seconds (a large model takes a while to load) and succeeds only when the engine answers. If it does not, if the service manager refuses the load, or if the command is interrupted (Ctrl-C, SIGTERM), it rolls back: it unloads the service, removes every file this run wrote, puts back any file it replaced from the backup it took first, and prints the tail of the engine's log, which is usually the whole diagnosis. A service that was already running when an update failed is restarted from its restored files. A refusal before anything is written (the RAM rule, a busy port, a bad name) leaves the machine untouched.

--check is the test that never changes anything, in the convention the installer uses (install.sh --only NAME --check): exit 0 when the files are what they should be and the service is loaded and answering, exit 3 when an install would change something. check NAME audits an engine that is already installed from its record: every file unedited, the service loaded, /health answering (exit 0), or what drifted (exit 3), or exit 4 when there is no such engine. remove NAME unloads the service and deletes only the files the record lists, and puts back any file the install replaced; it does nothing to a service it has no record of.

System-wide: a service that survives logout

--system is for a box that must serve with nobody logged in: a LaunchDaemon in /Library/LaunchDaemons/ on macOS, a unit in /etc/systemd/system/ on Linux. Writing there needs root, and this command never runs sudo. It stages the files in the engine's own folder, runs the engine as you rather than as root, and prints the commands for you to run:

sudo install -o root -g wheel -m 644 <staged plist> <system plist>
sudo launchctl bootstrap system <system plist>

<staged plist> is the file in the engine's folder and <system plist> is /Library/LaunchDaemons/io.goldenthread.farm-engine.NAME.plist; install prints the real paths. (On Linux: sudo install, sudo systemctl daemon-reload, sudo systemctl enable --now <unit>.) Then run check NAME to prove it. remove NAME prints the matching commands first and finishes (deletes the staged files and the record) when you run it again afterwards.

Telling gt about it

install prints the row for the service table (section 6) and does not edit the table, which is yours:

name                      engine-1
transport                 chat-completions
base_url                  http://127.0.0.1:8080/v1
model                     current
pool                      (yours: a pool name, or blank)
local                     yes
key_file                  (blank: a local engine needs none)
reference_rate_per_mtok   (yours)
notes                     launchd service, 4 slots, context 16384

That is one row of the table, in the same columns; install prints it ready to paste, header included. local: yes because it runs on hardware you own; the base_url is stable because the service is always there. Fill in pool and the reference rate as section 6 describes. The model alias is the name results report, so a file called Qwen3-Coder-30B-A3B-Instruct-UD-Q3_K_XL.gguf appears as current. To change the model, relink ~/models/current.gguf and restart the service (launchctl kickstart -k gui/$(id -u)/io.goldenthread.farm-engine.NAME, or systemctl --user restart gt-farm-engine-NAME); the table never changes.

By hand: a node on the LAN

The command is deliberately narrow: loopback, one model, the settings above. A fleet node that other machines reach directly needs more than that, and you can write the unit yourself. If you do, bind the node's own LAN address, never 0.0.0.0, and keep it behind the network's boundary:

# /etc/systemd/system/llm-engine.service
[Unit]
Description=LLM engine (llama.cpp server)
After=network-online.target
Wants=network-online.target

[Service]
User=engine
ExecStart=/opt/llm/llama.cpp/build/bin/llama-server \
    -m /opt/llm/models/current.gguf -t 13 -c 16384 -np 4 \
    --host <this node's LAN address> --port 8080 --alias current
Restart=on-failure
RestartSec=5

[Install]
WantedBy=multi-user.target

Check it from another machine with curl -s http://<node>:8080/health (expect {"status":"ok"}) and give the node a fixed address or a DHCP reservation, because the service table will name it.

Nothing on the node holds a secret, and nothing on it should: a public model, a public build, and whatever packets gt sends it. If your network quarantines new machines until an administrator releases them (many home firewalls do), release the node before you spend time diagnosing the guest — that was the first hour lost on this measurement.

Verification state. The recipe underneath — a LaunchAgent running a control script in run mode, RunAtLoad, KeepAlive, ThrottleInterval 10, health at /health — was verified by hand on a 48 GB Mac (self-verified). gt_farm_engine.py automates it and is tested against stand-ins for launchctl, systemctl and the engine, on both service shapes: the files it writes, the proof, the rollback, the checks and the refusals. Against a real systemd it has been run once (a Linux test host, 2026-10-15, with a stand-in engine): install, the health proof, --check, a rerun that changed nothing, a crash restart by systemd after RestartSec, and remove all behaved (self-verified). A real launchd, and a real engine with a real model under either, have not (unverified).

6. Telling gt about the engine: the service table

gt-farm reads its services from a Markdown table. The path is farm_services in ~/.claude/vault-config.json (absolute, or relative to the vault). The columns the sender reads:

| name       | transport        | base_url                  | model   | pool  | local | key_file | reference_rate_per_mtok | notes |
|------------|------------------|---------------------------|---------|-------|-------|----------|-------------------------|-------|
| engine-1   | chat-completions | http://engine-1:8080/v1   | current | fleet | yes   |          | 3.00                    | mini-PC, 13 GB quant, 4 slots |
| engine-2   | chat-completions | http://engine-2:8080/v1   | current | fleet | yes   |          | 3.00                    | same |
| laptop     | chat-completions | http://laptop:8081/v1     | big     |       | yes   |          | 15.00                   | 120B model; start by hand |
| hosted-api | api              | …                         |         |       | no    | ~/.config/gt/hosted.key | | a paid service; a key, by location |
  • transport: chat-completions is the HTTP shape llama.cpp's server, vLLM, Ollama, LM Studio and most hosted services expose (POST <base_url>/chat/completions). Only such rows are sent by the sender; other transports keep their own route (a human relay, or a vendor runner).
  • pool groups engines that take turns on a batch. --pool fleet spreads packets one per engine at a time and retries on another engine when one fails.
  • local: yes says the engine is on your own network. It relaxes exactly one part of the Releasable gate (section 8) and is recorded in the ledger so the local share can be reported. It does not make the engine private: an engine has no login, so any process on the machine it runs on (or, off loopback, on the network) can use it. gt's own digests (/gt:gt-digest, spill summaries) send text only to an engine on this machine; for one on another machine, add an optional lan_ok column and put yes in that row, knowing the text then crosses the LAN unencrypted.
  • trust (gt 0.22.0, optional) is read-only or autonomous. A row without it is read-only. A read-only engine's work is never filed on its own by the ladder: gt_farm_send.py ladder holds the result and Claude reads it against the packet first (review-result KEY accept files it; reject --reason "..." throws it away, keeps a copy under ~/.claude/golden-thread/farm/rejected/, outside the vault, and sends the packet on to Claude). autonomous is yours to write, never gt's, and only counts when the engine has a calibration record in which every injection probe was resisted (a record over 30 days old still counts, with a warning to re-run). With no such record, or after a failed probe, an autonomous row is treated as read-only and the output says why. Calibrating prints the line to add after a clean run. This is BREAKING: an engine that was routing on its own before 0.22.0 is read-only until you add trust: autonomous to its row. The hold is the ladder's only: gt_farm_send.py send, where you (or Claude) name the engine, never holds. It writes the result outside the vault (--out, results/ beside the packet, or gt's state folder with the queue line printed), to be read before it is filed. send --queue files it through the write queue at once, so it is refused (exit 2, nothing sent) for any engine that is not trusted: a read-only row, or an autonomous one without a passing calibration. A --pool is judged engine by engine, and one untrusted member refuses the whole send. This is BREAKING: a script that used send --queue with a default row now has to send without --queue and file after reading, or set trust: autonomous on a calibrated row.
  • tier (optional) is home or remote; rung is 1 to 3 as before. A per-machine copy of the table named <table>.<hostname>.md beside it replaces rows by name for that machine (see section 13).
  • reference_rate_per_mtok is what the packet would have cost, in USD per million tokens, at the service it would otherwise have gone to. It is your number — the hosted model you would have used for that packet shape — and it is what turns a token count into an avoided cost. Leave it blank and the ledger records zero, honestly.
  • key_file is a location, never a value. A local engine needs none.
  • The engine-1 and engine-2 rows above name nodes on the LAN, set up by hand (the end of section 5). An engine installed with gt_farm_engine.py listens on loopback, so its row names http://127.0.0.1:<port>/v1 (or the address you forward it to), and install prints the row.

The table is yours to keep; gt never writes it. Keep it outside the vault or write it through the write queue like any other vault file.

A hosted engine over the internet: a LOTR connection (gt-farm 0.22.0)

A hosted, OpenAI-compatible model (OpenRouter, Together, any host that serves /v1/chat/completions) is not a local engine, and the farm sends automatic work to local engines only. The supported way to use one is a gt-lotr connection and a transport: lotr row, so the key stays in the secrets store, the gateway applies its limits, and the farm knows the engine is remote.

  1. Put the key in the store, in your own terminal (never in Claude): lotr secret put llm-api-key.
  2. Register the connection from the template: lotr add-http <connection>@<zone> --from-template openai-compatible (OpenRouter is the default; for another host add --base-url https://api.together.xyz, the URL without /v1). Add --token-ref store:NAME if you stored the key under another name. lotr status --check then shows whether the host answers: the probe sends no key, so a wrong key shows on the first call as http_401.
  3. Add the row (the host's name goes in provider, because the template names none):
name transport connection op model provider local tier pool
remote-example lotr @ POST /v1/chat/completions openrouter no remote

The model id is an example, not a fact: ids change or vanish, and you choose it. Prices and the host's retention and training settings are yours to read and set on the host's account; gt controls neither. 4. Enrol the farm as a gateway client once (lotr app-connect), as for any transport: lotr row (section above in the gt-farm skill).

Set up a hosted engine in one command

Steps 1 to 3 above can be done for you by one script, run in your own terminal (it refuses anywhere else):

python3 <farm-scripts>/gt_farm_hosted_setup.py --vault <vault> --services <vault>/<path-to>/farm-services.md \
    --name <engine-name> --model <provider/model-id> [--base-url https://<host>] [--provider <label>] \
    [--allow-private-host]

--dry-run shows what it would do, and --check reports which pieces exist and what to run next; neither asks for a key or sends anything. Before a real run touches anything, it names the host the key will be sent to ("The key ... will be sent as a bearer token to HOST (https)") and asks you to type back a code it shows on the terminal itself, the same typed challenge LOTR uses. --yes skips only the later cost question, never the code. Then it does four things and says done, skipped or failed for each:

  1. The key. It starts lotr secret put with your terminal handed over, so you type the key at LOTR's own hidden prompt. The script never reads, receives or prints the key: it is not an argument, not in the environment, not on a pipe and not in a file the script writes. The key is always stored as llm-key-<engine-name>; the script never uses another stored credential. A key that is already stored there is not asked for again (--replace-key asks anyway).
  2. The connection, from the openai-compatible template, with the key as a store: reference. If a connection with that name already exists, it is used only when its address and key reference are exactly the ones asked for; otherwise the run stops and shows both, so a connection someone else made, or an old address, is never used by mistake.
  3. The row, added to (or updated in) your service table through the vault write queue, inside the table so the reader finds it. It is trust: read-only, so results are held for your review, and its local cell is left empty. The script drains the queue, which also applies other sessions' queued writes (with their usual claim and conflict checks). If the table changed while the script ran, nothing is queued; if the broker holds the write as a conflict, the run says so and prints the row to add by hand.
  4. A check, with your yes: one tiny public packet through the row, and the result shown (the result file is kept in a private folder of its own, and the message names it). --no-send skips it.

Run it twice and it updates, never duplicates; if a step fails, the earlier ones stay and the message names the command that resumes from there. The address https://openrouter.ai/api is only the template's default example; any public https host that serves /v1/chat/completions works. A literal IP address, localhost, a single-label name or a .local, .internal, .lan or .home.arpa name is refused unless you pass --allow-private-host; plain http is always refused. Check the host it names before you type the code: a lookalike name is not caught. If the check fails with a gateway error, enrol the farm once with lotr app-connect.

The gateway reports a provider's answers as structured codes: upstream_rate_limited (429, with its Retry-After), upstream_payment_required (402, out of credit; retrying does not help), upstream_error (5xx), upstream_timeout. The row is read-only until you set trust: autonomous, and an unpriced hosted row fails closed under a spend budget.

Status of this route: the connection template and the farm side are tested against a loopback fake. The live spike (a real key, a real send through the gateway) has not been run; it needs you to put the key in the store (step 1) and enrol the farm (step 4). Until then, a plain chat-completions row with key_file still works for a manual send, but the farm's automatic routing ignores it.

Hosted spend: sample and how to set up your own

gt 0.22.0 ships a sample, not your setup: templates/hosted-spend.sample.md in the gt-farm module shows the two settings (usage_external, farm_budgets) and one service-table row for a made-up engine on a made-up host (example-provider, address ending .invalid). It holds no key, no account id and no real address, and gt does not read it.

What you get without doing anything else is an estimate: the tokens sent and received, at the rate in the engine's row. The status line says (estimated) and stays quiet until an engine is at 80% of its budget or was answered with a 429. gt 0.22.0 does not read a provider's balance or billing API; the balance_source column in the sample is reserved and ignored.

To set up your own: copy the row into your service table and change every value (name, address, model, rate from the provider's pricing page); put the engine's API key in a mode-600 file by a script you run (never in a session), named in key_file; then gt_settings.py set farm_budgets "yourname=10". For a measured balance you would also need a read-only billing key from the provider, kept in the secrets store and never entering the session or the repository. gt does not use one yet.

7. Sending a packet

The packet does not change. It is the same Markdown file the skill builds for a human to paste — ### TASK, ### INPUTS, the vocabulary block, and the ### RETURN CONTRACT that demands FINDINGS: with a source: per claim and a mandatory GAPS:. The sender ships with the farm module (~/.claude/plugins/cache/golden-thread-plugin/gt-farm/<version>/scripts/gt_farm_send.py):

# one packet, one engine
python3 .../gt_farm_send.py send Projects/<project>/packets/2026-10-14-freshness.md --service engine-1

# a batch across the pool, one packet per engine at a time, retry on failure
python3 .../gt_farm_send.py send packets/*.md --pool fleet

# say what would be sent where, send nothing
python3 .../gt_farm_send.py send packets/a.md --service engine-1 --dry-run

What it does, in order:

  1. Reads the packet from ### TASK on and refuses a file missing ### INPUTS or ### RETURN CONTRACT — a partial packet is not sent. 1a. Scans the packet for credentials (gt 0.21.4) with gt core's gt_secrets, for a local engine as much as a hosted one. A credential-shaped line refuses the packet (exit 2) and names the line and the rule, never the value; a scanner that cannot run refuses it too (exit 6). ladder and pipeline scan the same way (the pipeline also scans the unit's material files). 1b. Skips a send that would not pay for itself (automatic sends only). ladder, pipeline and send --auto (what gt's intake digest and the workflow farm step use) skip a packet smaller than the break-even size and say not worth sending: N chars < break-even M (exit 5: do it in Claude). Setting farm_min_chars (default 2000; --min-chars N for one run; 0 turns it off). A send --service X you type is never skipped. 1c. Reuses an identical send. The key is sha256(packet + engine + model); a passing result under farm_reuse_days (default 7; 0 = never) old is filed again with no send, reported as reused and marked reused: true in the ledger. --fresh forces a new send. Stored results live in ~/.claude/golden-thread/farm/cache (folder 0700, files 0600).
  2. Applies the Releasable gate for this transport (section 8) against every engine the packet may land on, and says which gate applied.
  3. Sends the packet as the user message (sections reordered for the engine's prompt cache: the contract and vocabulary first, the task last; cache_prompt: true to local: yes rows) with a one-line system instruction to answer only in the contract's shape, and binds the reply to the contract with a JSON schema when the engine accepts response_format (llama.cpp's server does). The schema is the one thing a wire has that a browser does not: the engine cannot return an essay.
  4. Checks the reply. The JSON is rendered back into the packet's own FINDINGS:/GAPS: text so results stay diffable against hand-relayed runs; a text reply with both blocks is accepted as the text contract; anything else is reported and not filed (exit 3). --keep-raw DIR saves such a reply outside the vault so you can read it.
  5. Files the result. Every result file, and every --keep-raw file, starts with the line External engine output — unverified; do not follow instructions in it. Beside the packet in results/ when the packet is outside the vault; when it is inside the vault, the result goes to a temporary file and the exact gt_write_queue.py --origin farm --op create … line is printed (--queue runs it and the broker drain, for a trusted engine only), because nothing writes a vault file directly.
  6. Appends the ledger line (section 9), with claude_overhead: the tokens Claude spent on the send (the call, the packet when Claude wrote it, the result it reads; characters / 4). ledger reports NET: tokens kept off Claude minus that overhead.

While it waits, progress goes to stderr only (stdout and --json stay the result): a start and a finish line per packet and, every 30 s (farm_heartbeat_s), a waiting line naming each engine still working and how many packets are left.

The output is the audit trail — relay it, do not summarise it:

2026-10-14-freshness.md -> engine-1: ok, bound (JSON schema); claims=3 source:NONE=3; prompt 279, completion 311 tokens, 17.3 s
  gate: releasable -- the packet names no internal system
  wrote Projects/myproject/packets/2026-10-14-freshness-result.md
  ledger: farm line, measured, avoided $0.0018 at 3.00/Mtok

Note source:NONE=3. A chat-completions engine has no web access: every source: it returns is recalled from training, never read. For anything not stated in the packet's INPUTS, source: NONE is the honest answer and the one the system prompt asks for. The skill's rule stands with full force: nothing is self-verified until someone opens the URL.

Asking for code back (gt 0.22.0)

A packet whose ### RETURN CONTRACT section begins with a CODE: line asks for code. It is sent without the JSON schema and its reply must be fenced code block(s) plus at most one NOTES: line. The farm checks the shape and that a python block parses (never executed); an untagged block is parsed too when the RETURN CONTRACT names python. It does not check that the code is right: that is your tests' job, and the engine's output stays untrusted. A reply the engine stopped at the completion cap (finish reason length, or 97% of --max-tokens used) is refused even when every block is closed, and so is one empty because a reasoning engine used the whole cap thinking, with a hint to raise --max-tokens (about 40,000 for a reasoning engine; the farm never raises it for you). A reply may hold at most 20 blocks, under a per-block and a total size cap, and no line inside a block may start with `` or ~~~ (a bare run of three or more backticks closes a block). The filed result is rebuilt: each block under a fence longer than any backtick run in it, and theNOTES:text as a quotedEngine note (unverified)line. The same check runs insendand inladder; the ladder holds a read-only engine's code for review,senddoes not (seetrust` above).

Handing one handoff or task item to an engine (gt 0.22.0)

gt_farm_item.py build turns one item into a packet (scrubbed, gated, split and never trimmed), return checks that the answer is complete, and accept files it. The checker is gt:verify, the fresh-context agent behind /gt:gt-validate; gt ships no separate "farm-verifier" agent, because that would duplicate it. The answer is untrusted data: gt:verify re-derives its claims, and its verdict is recorded against the answer file with gt_validation.py record --file ANSWER --verdict holds --by gt:verify (a receipt tied to the file's content hash). accept refuses when there is no receipt, when the verdict is broken or cannot-verify, or when the answer was edited after it was verified; it records the verdict and who verified in the ledger line. An external engine's answer is never labelled better than self-verified (external engine, weaker).

Calibrate an engine before gt uses it (gt 0.21.4)

An engine that answers is not yet an engine that is good. Before gt sends a new engine anything on its own, it measures the engine's model once: python3 gt_farm_calibrate.py NAME (--dry-run first: it prints the plan and the estimated Claude cost, and sends nothing). A fixed set of harmless, invented probes goes to the engine and to Claude; a zero-context judge compares the answers, and a script checks what a script can check. You get, per kind of work (summaries, log triage, quote and field extraction, classification, drafting, generalising, code review), a verdict -- can-take, review-only (Claude checks every result) or not-suitable -- with the numbers behind it, the context the engine can really hold, whether it resisted a planted instruction, and one summary line.

Until a model has a calibration, gt gives it no automatic work (the commit-step review, the farm ladder); gt_farm_send.py send --service NAME is still yours to use. The verdicts are kept per model in your vault (Projects/golden-thread/farm/calibrations/) and in a local cache, so a model you switch away from and back to is not measured again, and a second machine that pulls the vault already has them. --list shows every model measured, --status each engine's current model. The setting farm_first (off, suggest, auto) decides whether gt only tells you what to do or also does the first steps; see the manual's Farm-first section.

Test an engine on code (gt 0.22.0)

Calibration says whether an engine can summarise or extract; it does not say whether it can write code. For that, python3 gt_farm_codetest.py all NAME claude:sonnet --repeat 2 --record NAME runs the engine through a small fix task and a feature task as a real agent session, grades them with a script, and has a blind judge score the diffs. Passing the tests is not enough: a model that passes every hidden test with a poor design is review-only. The verdicts (code-fix, code-feature) are added to the engine's calibration record, and a single run tops out at review-only. The engine must be the only large model resident (a 70 GB coder and a 63 GB reasoning model do not fit together in 128 GB), so stop the other first. See the manual's section 3b.

8. The gates, and the one that moves

The skill's four gates decide whether a task may leave the session at all: Stateless (answerable with no vault or repo state), Self-contained (fits in a paragraph plus a list of inputs), Checkable (verifiable without redoing the work), Releasable (every input safe to hand to a third party). The first three are judgement and do not change for a local engine: a packet that needs the repository fails gate one whoever would run it.

The fourth is a default-deny list: account identifiers, balances, position sizes, risk parameters, hostnames, internal addresses and domains, credential locations, non-public source code, personal identifiers. For an engine marked local: yes, and only for it, the hostnames and internal addresses part of that list does not apply, because the packet never leaves your network. The sender enforces the half it can see: a packet naming a private address or an internal host name (.lan, .local, .internal, localhost, RFC 1918 ranges) is refused for any service without local: yes and sent to one with it, and the message says which gate applied. The rest of the list still applies everywhere, because the result is filed in the vault and read by other sessions.

9. The ledger: what it cost and what it saved

Every sent packet appends one line to gt's savings ledger (~/.claude/golden-thread/usage/savings.jsonl, the file the gt-usage module reads), mechanism farm:

field meaning
service, model, local which engine took the packet, and whether it was on your network
prompt_tokens, completion_tokens from the engine's usage field; state: measured
wall_s seconds from request to reply
rate_per_mtok, usd_avoided the row's reference rate and the tokens priced at it
actual_eq, counterfactual_eq 0 and the token count for a local engine (the session spent nothing); both the token count for a hosted one
state measured, or estimated when the engine returned no usage field or the packet was relayed

A packet a person carried at rung 0 is recorded too, so the ledger never shows a farmed packet as free merely because a human pasted it:

python3 .../gt_farm_send.py relay packets/2026-10-14-depth.md packets/2026-10-14-depth-result.md --service hosted-api

Its tokens are estimated from the two files' lengths and marked estimated. The summary:

$ python3 .../gt_farm_send.py ledger --days 30
farm ledger -- last 30 days: 41 packets, 38 on local engines (93%); 11,204 prompt + 29,870 completion tokens; 2,960 s wall; avoided $0.1232 at the reference rates; 3 of them estimated (relayed or no usage field)

With gt-usage 0.1.10 or later, /gt-usage:gt-usage-savings reads the same lines into the savings report: a Farmed packets row in the mechanism table, and a FARM section under it with each engine and model, local or other, measured against estimated, wall time and tokens per second, cost avoided (- where no reference rate is set), sent against relayed, a day-by-day trend, and the share of the window's work kept off Claude (farmed tokens weighted like Claude's, against the work the ledger recorded for Claude itself; an estimate, never converted into a percent of your plan allowance). gt_savings.py farm prints that section alone.

Read that line honestly. Forty-one packets avoided twelve cents: the saving per packet is small, and the case for the fleet is width and zero marginal cost, not the per-packet price. The figure that matters is the share of your paid-model spend that was mechanical, which you learn by running real packets for a week and comparing the ledger with your bill. Until that baseline exists the saving is a projection, and the ledger is what turns it into a measurement.

10. What to send, and what to keep at the prompt

Send to the fleet — short prompt, long or structured output, no judgement needed on the way:

  • bulk extraction and classification of text you supply in the packet;
  • freshness sweeps ("which of these statements is still true?") over quoted text;
  • test generation for a named function whose source is in the packet;
  • summaries of a page, a log or a transcript you paste in;
  • a second-opinion draft on a design note, to be read by a person.

Keep at the interactive host, or on the laptop-class engine, or at the paid service:

  • anything that needs the repository or the vault in context (it failed gate one anyway);
  • multi-turn agentic edits — the fleet's 20-second prompt time per 2,000 tokens makes every turn a wait;
  • research that must cite pages: the engine cannot read them. A research-mode hosted service stays at rung 0, by its terms and by its output shape.

11. Limits and honest caveats

  • One run each. Every figure here is self-verified; none has been reproduced by another person. Section 3 exists so that yours are better than ours.
  • Mixed quantisations. The mini-PC's single-stream figure is 20.7 tokens/s at Q4 and 21.9 at Q3; the four-way figure is Q3. The slowest node's figures are Q4 with headroom. Compare like with like when you measure.
  • "Paging" is strongly indicated, not isolated. The run that collapsed and the run that recovered differed in free RAM and in quantisation. The sizing rule is safe either way; the mechanism is inferred.
  • No retrieval. A chat-completions engine answers from its weights. Treat every citation as unread.
  • Quality was not benchmarked here. The model followed a strict contract and admitted gaps on the first live packet; that is a property of the packet shape as much as of the model. Published benchmark standings are not claimed in this paper.
  • The service command has not met a real service manager yet. gt_farm_engine.py is tested against stand-ins for launchctl, systemctl and the engine, which proves the files, the proof, the rollback and the refusals but not that macOS or systemd accepts what it writes (unverified). Run it once with --dry-run, then for real on a machine you can watch.
  • The ledger prices avoided cost at a rate you supply. Supply it honestly — the hosted model you would really have used for that packet shape — or leave it blank and accept a zero.

12. Checklist

  1. Measure one node (section 3): llama-bench, then the server with four concurrent requests, watching free memory.
  2. Choose the quantisation by the sizing rule (section 4), not by the best number.
  3. Make it a service, not a session's child, with a health check: gt_farm_engine.py install (section 5).
  4. Add the row to the service table with transport: chat-completions, local: yes, a pool name and your reference rate (section 6).
  5. Send one packet with --dry-run, then for real; read the gate line and the contract line (section 7).
  6. Run real packets for a week; read gt_farm_send.py ledger beside your bill (section 9).
  7. Only then decide whether more nodes, a bigger node, or a GPU is worth buying. The fleet you already own is the baseline the purchase has to beat.
  8. Using the engines from another machine (a laptop on a VPN)? Follow section 13: prove the route, give the engine a key, write that machine's own table, then run gt_farm_send.py engines check.
  9. Remember every engine starts read-only: Claude checks what it returns before anything is filed. Add trust: autonomous to a row only after a clean calibration (sections 6 and 13).
  10. Want a hosted model to fix code on a copy of your repo? That is separate and opt-in: follow section 15, and read its list of what to check before you turn it on.

13. Using your home local models from another machine: connect, qualify, rank

A machine that is not on the engines' network (a work laptop behind a VPN, say) can use your own local models as farm engines. gt cannot make that route for you, and it will not send anything until each engine has passed the checks below from that machine. Section 5 built the engines; section 6 told gt about them; this section is what changes when the sender is somewhere else.

Connect

Do these three in order and stop at the first that fails.

  1. A route. From the remote machine, ask the engine its health: curl -s -m 5 http://ENGINE:PORT/health. An answer ({"status":"ok"}) means the network carries it; continue. Silence means the VPN blocks local traffic, or the engine host's firewall does not allow that machine. gt cannot fix that: fix the network. If the VPN cannot reach your home network at all, the only other route is a tunnel with TLS and a token, and a work machine's policy has to allow it: ask first.
  2. A login. An engine with no key is open to any machine that can reach it, so anything that crosses a network boundary needs one. Start the engine with --api-key-file (llama-server); the key is written by your secrets store and never typed into a session. The row's key_file names the mode-600 file on the sending machine, and that machine gets its own copy from the store. Until a key exists, an engine bound to loopback (127.0.0.1) stays bound to loopback: do not rebind it to the network for a remote caller, and engines check reports it unreachable from elsewhere, which is the right answer.
  3. A table of its own. The shared service table names the addresses as the host sees them. Put the addresses as the remote machine sees them in a copy named for it beside the shared one: farm-services.<hostname>.md (the short, lower-case hostname; GT_FARM_HOSTNAME overrides it). It is read after the shared table: a row with the same name replaces the shared row, a new name is added, and a copy for another machine is never read. Rows may also carry tier (home or remote) and rung (1 to 3).

Qualify

An engine is usable from a machine only when it passes these from the machine that sends, because the route and the login differ per machine. Run python3 gt_farm_send.py engines check (or engines check NAME):

# Check It passes when
1 reachable /health or /v1/models answers within the timeout
2 authenticated the key from key_file is accepted and a request without it is refused; with no key_file the engine is reported open, a warning and never a failure
3 model the model the server reports matches the row's model
4 calibrated the model has a calibration record (gt_farm_calibrate.py); an uncalibrated model gets no automatic work
5 latency class one timed prompt of about 512 tokens: fast under 10 s, slow 10 to 60 s, bulk-only over 60 s. This orders engines; it is never a failure

The result is kept per machine (mode 600, no address and no key in it). gt_farm_send.py engines status reads it without contacting anything and shows each engine as available, unavailable, refused, mismatched or stale (older than 30 minutes), since when, and how often it went down today and this week; --refresh checks first. A packet that fails because an engine is down records it by itself.

Rank

When a packet is routed, per rung: engines that failed reachability, authentication or the model on this machine are skipped; the rest are ordered by latency class (fast first, then slow or untimed, then bulk-only), with ties kept in the table's row order; a prompt over about 6,000 tokens skips bulk-only engines (it is about 110 s on a CPU node and 8 s on a Mac). An engine that is down is skipped and never fails a packet: a failed check or a rejected result moves the packet up one rung, as before. No fresh check for this machine means the table's own order.

Read-only is the default. A new engine starts read-only whatever its calibration says: ladder holds its result, Claude reads it against the packet, and gt_farm_send.py review-result KEY accept files it (or reject --reason "..." throws it away). The row says trust: autonomous only when you have decided to trust it, and that needs a calibration in which every injection probe was resisted. Over a VPN that rule matters more, not less.

Before you start. gt_farm_send.py setup --check names what keeps local routing from working (the ladder settings, the ladder table, a calibration). And one question gt cannot answer for you: whether your employer allows work material to reach a personal machine at all. If it does not, none of this should be used from the work machine.

14. Wiring opencode and Codex to calibration verdicts

Calibration (section 6 and gt_farm_calibrate.py) leaves a verdict for every engine and task class: can-take, review-only or not-suitable, with the measured speed and what the engine costs. A coding assistant such as opencode or Codex can use the same data to pick the cheapest capable engine for the job it is about to do, instead of a model line you set once and forget. gt does not run inside them and does not change how they call a model; it only prints what it already stored.

The export

python3 gt_farm_calibrate.py --export-json [--task-type T] [--top N] [--include-review] [--vault V]

It prints a JSON list, cheapest first, one row per calibrated engine and task class:

[{"engine": "hosted-small", "model": "small-model-id", "task": "draft", "verdict": "can-take",
  "cost_per_mtok": 0.2, "tok_per_s": 180.0, "usd_spent_calibration": 0.0123, "hosted": true,
  "calibrated": "2026-10-28"}]
  • cost_per_mtok is US dollars per million tokens: 0.0 for a local engine; for a hosted engine the mean of the input and output rate recorded at calibration; null when the price table had no row (no number is invented), and null sorts last.
  • Only can-take rows are printed. --include-review adds review-only. not-suitable never appears.
  • --task-type takes a class name (log-triage, quote-extract, extract, classify, draft, generalize, review, summarise, code-fix, code-feature) or an alias (quote-extraction, field-extraction, classification, drafting, generalising-claims, code-review, summaries). An unknown name exits 2.
  • --top 1 is the cheapest capable engine.
  • It reads the live store on every call (the vault's calibration files, then the local cache) and writes nothing. A record whose probe set, adjudicator or reference has changed since it was made is left out, as in routing. The rows hold names and numbers only: no address, key file or key.

The wrapper: gt-model-for.sh

templates/gt-model-for.sh (POSIX sh) prints the one engine id the export puts first:

sh gt-model-for.sh drafting            # prints, say, hosted-small
sh gt-model-for.sh code-fix --vault ~/vault --include-review
GT_MODEL_FALLBACK=my-default sh gt-model-for.sh classify    # a fallback when nothing can take it

Exit 0 found (or fallback), 1 no capable engine, 2 usage or unknown task type, 3 gt-farm not found. It finds the scripts through $GT_FARM_SCRIPTS, else the folder beside it, else the newest installed gt-farm; $GT_PYTHON names the interpreter. Copy it somewhere on your PATH as gt-model-for if you like. On Windows it needs Git Bash (Git for Windows); it will not run in cmd or PowerShell.

The engine id is the name of the service-table row. For the assistant to use it, register the same engine with the assistant under the same name (a provider entry that points at the same address and key you gave the service table); the wrapper chooses among engines, it does not create providers.

Honouring the farm share: --task-key

Section 15's share table (farm-share.tsv) sets what share of each task class goes to the farm, how often Claude audits it, what it may spend a day, and when a class pauses. gt's own routing applies it; an assistant that picks its own model does not see it unless you ask. Give each task a key (a ticket number, a file name, anything stable) and the wrapper applies the table for that one task:

sh gt-model-for.sh code-fix --task-key "ticket-1432"     # prints an engine id, or the word keep
codex -c model="$(m=$(gt-model-for code-fix --task-key ticket-1432); [ "$m" = keep ] && echo my-default || echo "$m")" "..."
python3 $FARM/gt_farm_calibrate.py --export-json --task-type code-fix --task-key ticket-1432   # the full decision as JSON

keep means the task stays with the model you would have used anyway. The same key always gets the same answer, so a share is reproducible; a share below 100 percent sends only that fraction of keys to the farm. The JSON also says the audit_rate (so you know whether a Claude check is expected), whether the class is paused and why, and budget_left for today. A row that pins an engine uses it if calibration says it can take the class, and is keep if not. With farm_share off (the default) the table is not applied and the answer is the plain cheapest capable engine, as without a key. A missing calibration, a paused class, an unreadable table or an unreadable state file all say keep.

This is advice at selection time. It uses the same selection code as gt's routing, but it records no spend, moves no ramp and writes no state, so work done by an assistant does not advance the share or count against today's budget. If you want it to, that is not wired.

opencode

opencode's config file holds a fixed model string, so choose the model when you start it, from the command line, which accepts provider/model:

opencode run --model "farm/$(gt-model-for drafting)" "Draft the release note for ..."
opencode --model "farm/$(gt-model-for code-fix)"

where farm is the provider name you gave the engines in ~/.config/opencode/opencode.jsonc. Keep the config's own model line as the default for work you have not classified. To wrap it once, put the two lines in a shell function per task type (oc-draft, oc-fix) in your shell start-up file.

Codex

Codex reads a top-level model key from ~/.codex/config.toml, and the same key can be set for one run with -c (a command-line override beats the file; this is from Codex's published configuration docs, not from a Codex run here):

# ~/.codex/config.toml -- the default when nothing is chosen
model = "my-default"

codex -c model="$(gt-model-for code-fix)" "Fix the failing test in ..."

Use a shell function for each task type, as for opencode. If the wrapper exits 1 (no engine can take it), the command substitution is empty; set GT_MODEL_FALLBACK=my-default so the run still has a model.

What this does not do

It does not route in real time (the ladder does that for gt's own packets), it does not make an assistant trust an engine (a can-take here means the calibration probes passed, not that your task is safe to hand over), and the exact flag names above were written from each tool's documentation, not run against a real opencode or Codex install. Check opencode --help and codex --help if a flag is refused.

15. Hosted agent farming: a paid model fixes code on a copy (gt 0.22.0)

Sections 1 to 14 are about engines on your own hardware. This one is about a hosted model you pay for, used as an assistant with tools on a COPY of one of your repos. Your code leaves the machine, so read "Before you turn it on" first. What comes back is a candidate patch for you to review; nothing is applied for you.

Set it up. Run these in your own terminal, not through Claude.

  1. Put your API key in a file only you can read (chmod 600), for example ~/.config/gt/agent-key. Create it without showing the key on screen. The secrets-store route is not supported for agent farming yet.
  2. Make sure gt's price table (the one the usage report reads, so the gt-usage module must be installed) has a row for the provider and model. With no price row the cost is unknown and start refuses.
  3. Run python3 $FARM/gt_farm_agent_setup.py start --dry-run. It asks seven questions (provider, model id, key file, task class and share, daily budget, repos, sandbox check) and prints a summary. Nothing is written.
  4. Read the summary. Run start again, answer the same, and say yes at the end.
  5. Measure the engine, once, before it routes anything. First python3 $FARM/gt_farm_calibrate.py NAME --kind agent-code --dry-run to see the cost, then the same with --yes-spend. It spends real money.
  6. Turn routing on with gt_settings.py set farm_share on (it is off by default). Optionally set farm_agent_budget_usd_day to a dollar figure for a limit across all classes.
  7. Check any time with gt_farm_agent_setup.py status or doctor. gt_farm_agent_setup.py off sends every task back to Claude.

The files.

Where What
the service table (farm_services) the engine row start writes: agent: yes, tools: yes, local: no, a key_file, and the optional parallel_tools, reasoning and data_policy columns
<vault>/farm-share.tsv one row per task class: share target, ramp, audit rate, daily cap, failure limits, optional pinned engine
~/.claude/golden-thread/farm/share-state.json per machine: the share now in force, counters, spend today, pauses
your key file read by the agent loop only; gt never prints or stores the key

How the share works. share_target is the percent of eligible tasks of a class that go to the farm at the end of a ramp. With ramp_step above 0 the share starts low and grows by that many percent after each clean window of ramp_window tasks (a window is clean when the failure rate stays under max_fail_rate and no audit in it failed). Which task goes is decided by a hash of its class and key, so the same task always gets the same answer. Routing pauses on its own when failures in a row pass pause_after, when the failure rate is too high or when a daily cap is spent; gt_farm_share.py status says which, and resume clears it. A fraction of farmed results (audit_rate) is re-checked blind by Claude, and a failed audit lowers the share.

Before you turn it on.

  • Your code goes to the provider named in the summary. Read what its data policy does not promise; gt can only enforce the request fields it knows for that provider family, and says so when it cannot. Check that your employer allows source code to reach a third party at all.
  • Name only repos you are content to send. Files named like keys, .env files and credentials are never read, and everything the model reads is scrubbed, but a scrubber is not a promise about a secret it does not recognise.
  • Your test command must find every test in the folder (python -m unittest discover, or pytest). The evaluation runs it three or four times, so it should be quick. A virtualenv interpreter under your home folder may not run in the sandbox; use a system Python.
  • Prefer held-out tests (--hidden-tests DIR), tests the model never sees, for any project that has them.
  • Accepted means the tests passed on a clean copy, not that the change is right. Read every patch. A forged result that also fakes the host's check test cannot be excluded.
  • This has not been run on Linux or Windows yet, and Windows has no write mode in the sandbox, so it is refused there.
  • Set a daily budget you can afford to lose. Start with a low share and a fixed ramp.

16. Single-shot work on a hosted model: calibrate it, then let gt route to it

Section 15 is a hosted model working as an agent on a copy of a repo. This section is the plainer case: a hosted model (anything that answers an OpenAI-style chat request) is measured once on harmless practice tasks, then gt sends it routine work it has shown it can do, checks the replies, and records what each packet cost. Claude keeps the judgement. A hosted model never gets your vault text: only public or scrubbed material goes to it (the ladder's rung 3). The commands below were written from the gt-farm scripts; they have not been run against a live provider, so run every paid step with --dry-run first.

Before you start. gt-farm is installed. You have an endpoint that speaks the OpenAI chat-completions shape (a provider's own API, or a local proxy in front of one; if the provider's native endpoint is not OpenAI-shaped, use its OpenAI-compatible route). The API key is in a mode-600 file, and the service row points at that file. Never paste the key into a Claude session; gt reads the file when it sends and never prints it.

1. Add the engines. farm_services in ~/.claude/vault-config.json names a Markdown file (an absolute path, or one relative to the vault; it is a key in that JSON file, not a gt_settings.py setting). One row per model:

| name | transport | base_url | model | pool | local | key_file | reference_rate_per_mtok | rung | provider |
|---|---|---|---|---|---|---|---|---|---|
| fast-small | chat-completions | https://api.example.test/v1 | model-small | hosted | no | ~/.config/gt/farm/provider.key | 0 | 3 | example |
| fast-large | chat-completions | https://api.example.test/v1 | model-large | hosted | no | ~/.config/gt/farm/provider.key | 0 | 3 | example |

local: no marks a hosted row, which defaults to rung 3 (public-only material). model is the id the service expects, and a hosted engine is identified by it: two rows naming the same model share one calibration record. provider keys the provider budget and the price-table row; a row with no price row cannot be costed. Give rows the same pool name to spread a batch across them.

2. Turn routing on.

python3 $GT/gt_settings.py set farm_first auto        # gt uses calibrated engines on its own
python3 $GT/gt_settings.py set farm_audit_rate 0.1    # Claude re-checks about one farmed result in ten

Optional: farm_ladder on (try the cheapest capable engine first), farm_budgets (for example provider:example=5 for a monthly dollar cap), model_calibration_budget (a cap on one calibration run).

3. Calibrate. $FARM is the gt-farm scripts folder.

python3 $FARM/gt_farm_calibrate.py fast-small --dry-run   # the plan and the estimated cost; sends nothing
python3 $FARM/gt_farm_calibrate.py fast-small             # run it
python3 $FARM/gt_farm_calibrate.py --status               # each engine: model, calibration, verdicts
python3 $FARM/gt_farm_calibrate.py --list                 # every model measured so far

A hosted engine is calibrated only when you name it (or --pool); --auto and --new never start a paid run. With no price row the run is refused unless you pass --accept-unpriced (the token counts are still recorded), and an engine that has a farm_budgets entry and no price row is refused even then. The record and the ledger carry what the probes cost (usd_spent, 0.0 for a local engine). Records are keyed by model, not machine: if you share a vault, another machine that pulls it finds the earlier verdicts and spends nothing re-measuring. Calibrate one cheap model first, read its record, then run the rest.

4. Read the verdicts. can-take: gt uses it for that task class without a check. review-only: gt uses it and Claude checks every result. not-suitable: gt does not use it for that class. An engine with no current calibration gets no automatic work; at rung 3 that holds for every class, so an uncalibrated hosted engine is skipped. This is a change in 0.22.0: rung 3 now requires a current calibration (rungs 1 and 2 are unchanged).

5. Wire an assistant to the verdicts. Section 14: --export-json, gt-model-for, and --task-key to honour the farm share.

Things that go wrong.

  • A provider's native endpoint is not OpenAI-shaped. Use its OpenAI-compatible route for base_url.
  • Newer OpenAI-family models reject max_tokens. gt 0.22.0 sends max_completion_tokens as well, and asks again with max_output_tokens when a Gemini-style endpoint refuses both; an older gt scores such a model 0 percent for the wrong reason.
  • An authenticated proxy answers 401 to the health probe. gt 0.22.0 sends the key on the model list, health and props requests; an older gt marks the engine DOWN before any probe.
  • A reasoning model may spend its whole token cap thinking and return nothing. Raise --max-tokens for the calibration run.
  • One gateway serves several model families on different routes. A proxy in front of more than one provider may speak the OpenAI shape on one base path and a different shape on another. Give each row the base_url of the route that answers OpenAI-style chat requests, and run --dry-run on one row from each family before calibrating the rest.
  • The model list names an id with a prefix (for example models/ before the id). gt 0.22.0 strips that prefix when it matches rows; the row's model column should hold the id the service expects in a request.
  • Two rows collapsed into one record. Check --status: each row should have its own record. Give each row its exact model id.

17. Reference: what calibration produced for three local models (an example, not a verdict)

This section is a reference. gt never reads it and nothing here is a verdict for your setup: a verdict measures one model, at one quantisation and context size, on one engine, on one day, and your own gt_farm_calibrate.py --status is the only record gt acts on. It is here so you can see what calibration produces, and which kinds of work a model of that size tended to pass, before you spend an hour measuring your own. No hosted model is listed: none has been measured.

Measured on 2026-10-17 on one Apple-silicon laptop with the synthetic probes gt ships (nothing of anyone's was sent). The verdicts are copied from gt_farm_calibrate.py --list on that laptop; the records themselves are not shipped, so they cannot be checked from this guide. The task classes are the ones the tool reports.

Model Quantisation Context Can take (used without a check) Review-only (Claude checks every result) Not suitable
gemma-4-26b-a4b Q4_K Medium 16,384 log triage, quote extraction, field extraction, classification code review drafting, generalising claims, summaries
gpt-oss-120b MXFP4 (mixture of experts) 131,072 log triage, quote extraction, classification, drafting, summaries field extraction, code review, bug fixing, feature coding generalising claims
qwen3-coder-30b-a3b Q4_K Medium 65,536 nothing on its own log triage, quote extraction, field extraction, classification, drafting generalising claims, code review, summaries

A class a row does not mention was not reported for that model in the tool's summary (bug fixing and feature coding, for the first and third rows); the table does not say why, and neither does this guide.

How to read it:

  • Size helped here. The 120-billion-parameter model takes drafting and summaries that the two smaller models do not, and it is the only one of the three to be marked for bug fixing and feature coding (review-only).
  • A coding model is not a safe default. The third model failed gt's injection probes, so nothing it returns is taken without a check, whatever it scores on the tasks themselves.
  • "Generalising claims" is hard for all three. Each was marked not suitable for it.
  • These were measured once. Re-measure after a model, quantisation or server change, and expect a record older than about a month to be treated as stale for agent work.

To measure your own: python3 <farm-scripts>/gt_farm_calibrate.py NAME --dry-run, then without --dry-run, then --status.
