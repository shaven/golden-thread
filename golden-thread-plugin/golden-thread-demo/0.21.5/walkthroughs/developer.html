A developer's first day

Someone who writes and ships code and wants the checks to be real. Practice project: demo-pizzabot (a pretend project; nothing here touches your real notes).

1. Load the project's context

What you are doing
Load the project's context
What to type
/gt:gt-open demo-pizzabot
What you will see
The project's design notes, decisions and open tasks, summarised, with a question about where to start.
Why it matters
The constraints you agreed last week are in front of you before you write a line.

2. Plan before code

What you are doing
Plan before code
What to type
/gt:gt-plan add a retry limit to the /order endpoint
What you will see
A phased plan with a goal and a done condition for each phase, and a wait for your approval.
Why it matters
A plan you can read costs less than a rewrite.

3. Build it test first

What you are doing
Build it test first
What to type
/gt:gt-implement
What you will see
One phase at a time, a failing test first, then the code; it stops on any failure and names the tests that ran.
Why it matters
You see which tests ran, not a claim that they did.

4. Run every check at once

What you are doing
Run every check at once
What to type
/gt:gt-allin
What you will see
A table of every check (scan, lint, tests, install health) and how many actually ran.
Why it matters
A check that was skipped is reported as skipped, never as passed.

5. Commit only with evidence

What you are doing
Commit only with evidence
What to type
/gt:gt-allin-commit
What you will see
A commit made only when a test receipt covers the staged files; it refuses on the default branch and never pushes.
Why it matters
The history holds only changes that were seen to pass.

6. Capture what you learned

What you are doing
Capture what you learned
What to type
/gt:gt-work
What you will see
Findings, decisions and design changes written to the project's notes.
Why it matters
The next session, yours or someone else's, starts with what you found out.
