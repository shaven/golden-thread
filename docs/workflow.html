The model

Facts move up the hierarchy as they prove general. They never move back down, and nothing is ever silently deleted.

sessionthe conversation you're having right now
↓  /gt-work
memory/*.mdthis project, this detail
↓  /gt-promote
research · decisionssettled findings and choices for this project
↓  /gt-promote
Knowledge/true for several projects — a platform behavior
↓  /gt-promote
global-memory/true everywhere, loaded in every session
The discipline that makes it work

Write the fact at the narrowest scope that is honest, and promote it only when a second project proves it general. A fact promoted too early becomes a rule you have to remember to disbelieve.

One-time setup

Already done for this vault. You'd only repeat it on a new machine.

/gt:gt-init

It writes ~/.claude/vault-config.json — the pointer every other skill reads — scaffolds the vault if missing, and adds a Golden Thread section to ~/.claude/CLAUDE.md. It is idempotent: re-running verifies rather than overwrites.

Starting a project

/gt:gt-create

Claude gathers a kebab-case slug (the name you'll use forever in /gt-open), a title, tags from the vault's taxonomy, whether it's a sub-project, whether it needs a runbook — and the topology.

Topology — the question worth answering carefully

Your situationTopology
A folder on this Maclocal
One repo, one server, server pulls from GitHubremote
Several servers, all reached through one gateway boxbastion-jump
Several servers, each reachable directlybastion-direct

Everything in this vault is bastion-direct except general, which is local.

This lands in source.md, and it is the file that stops Claude editing the wrong box. For bastion projects it also carries the file plan, marking each deployed file as:

  • static — byte-identical on every target. Deploy from one canonical copy.
  • unique — a per-server variant. Never copy one host's version over another's.
Why that distinction isn't bureaucracy

js/engine_common.js is static across app-01 and app-02 with nothing keeping them in sync — and the copies have already silently diverged once. dispatcher.js is unique across edge-01 and tools-01: same filename, different config, and copying one over the other would either kill production routing or point dev at real orders.

What you get

Projects/<slug>/
  README.md      status board — stage, next action
  source.md      where the code lives + deploy plan
  idea.md        your brain dump — IMMUTABLE after creation
  research.md    append-only dated findings
  decisions.md   append-only numbered ADRs
  design.md      current architecture — always describes now
  memory/
    MEMORY.md    index of session notes

Claude fills idea.md from what you actually said. Don't tidy it — it's the traceable "why" behind everything that follows, and it is never edited again.

The session rhythm

The loop you'll run hundreds of times.

Start — /gt:gt-open <slug>

Reads, in order: source.md → idea.md → research.md → decisions.md → design.md → spec.md → runbook.md, then the fleet page if source.md links one, then memory/MEMORY.md.

And it stops there

The individual memory/*.md files are not loaded. The index is one line per file with a description — enough to know what exists. Opening Automated Trading System costs ~53 lines instead of ~1,900.

Pull in detail as you need it: "read the MSTP3 notes", "what does the production backtest checklist say". That's the design working — you're spending context on what the task needs instead of on everything.

Middle — do the work

Normal Claude Code. Two habits worth keeping: check source.md before touching a server, and run /gt:gt-query before searching the web.

End — /gt:gt-work

The step people skip, and skipping it is what makes the vault decay. Claude proposes what to write and where:

Goes toWhat belongs there
research.mdDated findings, gotchas, measured behavior. New discoveries only — not things you already knew.
decisions.mdA numbered ADR: the decision, the context, the alternatives rejected. Only stable choices.
design.mdRewritten in place if the architecture changed. Always describes now.
memory/*.mdSession state — updated in place.
spec.mdCreated when the design is complete enough to hand off.

- **Context**: edge-01's copy gates the renderer block behind page_type
- **Rejected**: A single shared render.php — breaks edge-01's display gating
What does not belong in decisions.md

Anything you might change next session. Unstable things go in research.md or memory/. An ADR you reverse next week teaches the vault to lie to you.

Looking things up

/gt:gt-query

Reads index.md, follows wikilinks into Knowledge/ up to 2–3 hops, then falls back to grep across Knowledge/ and global-memory/, then project memory.

Be specific. "Quote API ticker key" finds the answer; "quote" finds noise. If a result carries status: stale, verify before acting on it. If nothing is found, that's a signal — either the knowledge isn't captured yet, or it's filed somewhere index.md doesn't reach, which /gt:gt-lint will tell you.

Promoting knowledge

/gt:gt-promote

The judgement call: has a second project proved this general?

From → ToWhen
memory/ → research/decisionsThe finding stopped changing session to session
project → Knowledge/A second project hit the same truth. It's a platform behavior, not a project quirk
Knowledge/ → global-memory/You need it in every session, for every project
anywhere → new projectThe idea doesn't belong to the project you're in

global-memory/ is expensive — it loads every session, everywhere. Six working rules live there now. Adding to it should feel like a decision, not a reflex.

Retiring

Nothing is deleted. A stale page gets status: stale and a note saying what superseded it. That's why Sources/2026-07-15 Server Topology.md still exists even though INFRASTRUCTURE.md replaced it — notes written before August still name those hosts, and a reader needs to be able to find out why.

Maintenance

Run these periodically, not every session.

CommandCadenceWhat it catches
/gt:gt-lintweekly, and after any ingestbroken links, orphan pages, index gaps, unlisted memory files, bloated global-memory, unfilled source.md
/gt:gt-refreshwhen upstream docs may have changedSources/ entries whose origin has moved on
/gt:gt-reviewwhen daily notes pile upuncaptured ideas and tasks worth promoting into projects
/gt:gt-runbook-lintwhen you have several runbooksprocedures duplicated across runbooks that should be shared

Lint findings you deliberately decline go in lint-declines.md as a suppress: line with the reason — a suppression without a reason is indistinguishable from a bug nobody got round to.

Where does this fact go?

The question that comes up constantly.

The factGoes to
"This ticker's preset is wrong"memory/ — session state
"Istio blocks PATCH in this project"research.md — dated finding
"We use POST for all mutations, and why"decisions.md — an ADR
"The system is structured like this now"design.md — overwrite
"The Quote API needs singular ticker"Knowledge/ — several projects hit it
"Always diff before overwriting prod"global-memory/ — everywhere, always
"How to restart the prod backtest"runbook.md — operational procedure
"Never scp without backing up first"PROTOCOL.md — process rule across projects
"Code for this lives on edge-01"source.md — topology
Two failure modes, in opposite directions

Filing too narrow — a platform truth buried in one project's memory, so the next project rediscovers it the hard way.

Filing too wide — a project quirk promoted to global-memory/, where it loads into every unrelated session as a rule that isn't true there.

When unsure, file narrow. Promotion is cheap and reversible; demotion isn't.
