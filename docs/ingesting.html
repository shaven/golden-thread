Ingesting an existing project

How to bring a project that already exists — with its own history, notes, CLAUDE.md and scattered memory files — into the vault. Written against what actually happened migrating this vault on 2026-08-15, including the two things that bit.

What ingest is, and isn't

Ingest is additive and non-destructive. It copies; it never moves or deletes from the original location. If it goes wrong, the source of truth is still wherever it was.

It is also not automatic. The script finds candidates and classifies them; you approve each group before anything is written. That approval step is the point — classification is a judgement about scope, and scope is the one thing a script can't infer reliably.

Before you start

Three things worth having ready, because being asked mid-flow is where people guess — and guess wrong.

  1. A slug. kebab-case, and the same one you'll use in /gt:gt-open forever.
  2. The topology. local (a folder here) · remote (one repo, one server, server pulls from GitHub) · bastion-jump (several servers behind one gateway) · bastion-direct (several servers, each reachable directly).
  3. A restore point, if you're restructuring something that already exists.
cd <target> && git add -A && git commit -m "Pre-ingest snapshot"

That last one is not ceremony. It's what made the migration on this vault safe to attempt at all.

Classify

This is the step that decides whether the vault is useful in six months.

GroupGoes toTest
decisionsdecisions.mdA stable rule or constraint. Would you be annoyed if it were violated?
researchresearch.mdA dated finding or gotcha. True, but might change.
designdesign.mdHow it's built now.
knowledgeKnowledge/ + Sources/True for other projects too — a platform behavior, not a project quirk.
global_memoryglobal-memory/Needed in every session, every project.
ideasnew project scaffoldDoesn't belong to this project at all.
skipstays putPersonal prefs (user.md) — session-level, not vault-level.

Say "show me each one" to review individually rather than approving a group.

Set the bar higher than it feels

A fact promoted to knowledge or global_memory on its first sighting is a guess about generality. Leave it in the project — /gt:gt-promote exists precisely so a second project can prove it.

Watch for the wikilink trap

The one that will actually bite you.

If the notes cross-reference each other by [[wikilink]], renaming or merging files silently destroys that graph. Obsidian resolves wikilinks by filename, so the moment project_foo.md stops existing, every [[project_foo]] anywhere in the vault dangles.

Measure before you restructure:

cd <vault>
echo "links:  $(grep -roh '\[\[[^]]*\]\]' --include='*.md' . | wc -l)"
echo "files:  $(grep -rl '\[\[' --include='*.md' . | wc -l)"
323
links found
63
of 74 files
219
to project_ notes

That measurement is why this migration kept every original filename intact and moved the files unchanged into memory/, rather than folding them into research.md as originally planned. The plan changed because the number came back bigger than expected.

Three ways out, in order of preference

  1. Keep the filenames. Move files as-is; the graph survives untouched. Costs nothing.
  2. Repoint the links. Fine for a handful of renames. Match the whole link — [[name]] and [[name|alias]] — never a substring.
  3. Drop them. Only if the graph genuinely has no value.
Substring matching will corrupt your links

A naive replace of reference_discord_webhook also rewrites [[reference_discord_webhook_mstp3]] — a different, still-existing note. Anchor the pattern to the closing brackets:

re.sub(r"\[\[" + re.escape(old) + r"(\|[^\]]*)?\]\]", ..., text)
Never repoint links inside Sources/

Those files are immutable; their links are supposed to point at the world as it was when they were captured. Suppress them in lint-declines.md instead.

Fill in source.md

New in v0.2.0, and the highest-value part of an ingest for a multi-server project.

The evidence is usually already in the material you just read — deploy scripts, hostnames in notes, install steps. Cross-reference it against ~/.ssh/config, which is authoritative for alias → address:

grep -iE '^host ' ~/.ssh/config

Fill in:

  • Topology — one of the four types.
  • Deployment targets — one row per role × env → host + path. This shape matters because one machine can serve several sites, and the same role exists in more than one environment.
  • File plan (bastion only) — every deployed file marked static (byte-identical everywhere) or unique (per-server variant).
  • Fleet — link the shared INFRASTRUCTURE.md rather than copying the host table in.
Read the notes for drift language

A note saying a file "drifted" or "had to be fixed separately on each box" is telling you it is static and currently unmanaged. Record that — it's the most useful sentence in the file.

Record only what the material states. Mark inferences TODO — verify and list them in the summary. A confidently wrong path is worse than a blank one, because a blank one gets checked.

Index the memory files

MEMORY.md is not decoration. It is the only thing /gt:gt-open reads — the files themselves load on demand. So each line has to carry enough signal to decide whether opening that file is worth it.

- [reference_quote_api](reference_quote_api.md) — live quote + daily-candle API at
  quotes.example.internal:6000; use it instead of the local cached files, which go stale

That's a useful line. — quote api notes is not.

Most notes already have a description: in frontmatter, which makes this mechanical:

m = re.search(r'^description:\s*"?(.*?)"?\s*$', frontmatter, re.M)

The largest project in this vault indexes 39 notes in 53 lines, against ~1,900 if every file were loaded — with the detail still one request away.

Verify

/gt:gt-lint

Expect findings on a first ingest. Triage them into three piles:

You broke itFix now, while you remember why. Mostly broken-link after renames.
Already brokenRecord in review-queue.md. Don't guess at a target — changing what a note claims is worse than leaving it dangling.
False positiveSuppress in lint-declines.md, with the reason.

Confirm which pile a link belongs in rather than assuming:

git grep -c "\[\[some_link\]\]" <pre-ingest-sha> -- '*.md'

On this vault: 28 findings → 3, and all 3 survivors were confirmed pre-existing against the pre-migration commit.

Wire and commit

Claude offers to add a Golden Thread section to the project's CLAUDE.md. For remote and bastion projects the code isn't on this machine, so skip it — the source.md targets are what matter.

Then commit, and record the ingest in log.md:

2026-08-15 [ingest] <source> → Projects/<slug> — N items migrated

Two things that bit

git mv needs the index to match the working tree. Moving .git up without committing first meant git still held the old paths, and every git mv failed until the move was committed.

Case-only renames fail on macOS. General → general needs a two-step: git mv General general-tmp && git mv general-tmp general.

Checklist

  • Commit a restore point
  • Decide the slug and topology up front
  • Count the wikilinks before renaming anything
  • Run /gt:gt-ingest and review each group, not just each batch
  • Fill source.md — mark inferences TODO, don't invent paths
  • Write MEMORY.md descriptions worth reading
  • Run /gt:gt-lint; sort findings into broke / already-broken / false-positive
  • Log unresolved questions in review-queue.md
  • Commit, and add an [ingest] line to log.md
